# Full config.json corpus: all artifact families included

**The corpus now includes every artifact record in the pinned configuration,
not just AndroidX and Google Play Services.**

| Configured family | Records |
|---|---:|
| AndroidX | 350 |
| Google Play Services | 94 |
| Firebase | **59** |
| Every other configured family | **214** |
| **Total** | **717** |

These are 705 distinct group/artifact coordinates across 161 Maven groups.
Different requested versions and dependency-only/no-binding records remain
separate original records. Nothing is filtered out by Maven group.

The source is the same saved
[`config.json` at revision 2393441675a6d82bb817ab7aa2df698c7ec929ce](https://github.com/dotnet/android-libraries/blob/2393441675a6d82bb817ab7aa2df698c7ec929ce/config.json).
This changes input scope, not the pinned upstream revision.

## What changed

- Removed the AndroidX/GMS allowlist from the independent comparison harness and
  the Gradle-backed corpus resolver.
- Added an actual Gradle inventory of all records before native resolution.
- Added full-config coverage checks that compare original records, multiplicity
  and flags, not merely a total or a config hash.
- The assembly-generation driver refuses an incomplete selection. The old
  444-record resolution is correctly rejected as missing 273 records, even
  though it used the same input file.
- The independent comparison now honors configured Maven Central repositories
  instead of always attempting Google Maven. CI uses the public Maven mirror.

The other families include ML Kit, Play libraries, Material, LiteRT, TensorFlow,
Glide, Accompanist, gRPC, OkHttp, Retrofit, RxJava, Kotlin and all other entries
actually present in the file.

## Actual input resolution

The complete 717-record input resolved to **716 selected modules and 646 native
archives**. All **59 Firebase records** are present in both the original inventory
and resolved selection. The generation planner also accounts for all 717 record
indexes exactly once.

Expanding the scope exposed standard Maven publication relocations:

- Error Prone type annotations -> Error Prone annotations.
- TensorFlow metadata -> LiteRT metadata.
- TensorFlow support -> LiteRT support.
- TensorFlow support API -> LiteRT support API.

Those are taken from the publishers' POM relocation declarations. Source
coordinates, destination, POM path and SHA-256 are preserved. Source GAV,
declared destination and POM hash are checked before substitution. We do not
silently pick a substitute SDK or label an empty relocation JAR as a successful
binding. The original configuration records remain in coverage.

The first combined resolution encountered an obsolete TensorFlow AAR selector
on its metadata-only relocation coordinate. Following the verified published
relocation resolves the real target instead of downloading a nonexistent AAR.
The final complete resolution passed, including an offline rerun.

## Status boundaries

**Corpus membership and native input resolution are complete. Expanded binding
assembly generation is not complete.** The previously published DLL ZIPs still
cover the old 444-record AndroidX/GMS subset; they do not yet include all Firebase
or other newly added roots.

The raw native audit finds 133,732 distinct JVM names and 3,510 duplicate names
in the attempted all-roots combination. That is not a count of public binding API
conflicts. Some configured native SDK choices cannot coexist in one Android
classpath. The strict duplicate gate continues to reject that combined native
graph; nothing was silently discarded to make it appear compatible.

This input expansion does not change the desired output architecture: one
canonical managed catalog with shared owners, not duplicated framework binding
assemblies in multiple compatibility ZIPs.
